# Execution Plans

执行计划是复杂任务的可恢复工作记录。它应当让一个只拥有当前仓库和该计划的新智能体继续工作，
无需依赖聊天记录或个人记忆。

## 生命周期

1. 在 `.harness/plans/active/` 新建 `YYYY-MM-DD-short-topic.md`。
2. 实施过程中持续更新进度、发现和决策；不要只在开始时写一次。
3. 每个阶段完成后记录验证命令和观察到的结果。
4. 验收完成后写结果总结，把计划移动到 `plans/completed/`。
5. 若任务取消或阻塞，也记录原因、已完成状态和安全恢复方式。

## 质量要求

- 自包含：解释项目内术语、相关路径、现状和目标行为。
- 面向结果：每个阶段都有可观察的验收条件，不只罗列编辑动作。
- 可恢复：记录已完成、下一步、命令和关键输出，不依赖未保存的终端上下文。
- 决策透明：写清选择、理由、替代方案和影响。
- 安全：标注真实远端调用、数据写入、迁移和回滚边界。
- 持续更新：计划与代码不一致时立即修正计划。

## 模板

```markdown
# <面向结果的任务名称>

状态：active
负责人：Codex / <name>
创建日期：YYYY-MM-DD
最后更新：YYYY-MM-DD HH:mm +08:00

## 目标与用户价值

说明完成后用户能够观察到什么，以及明确不在范围内的事项。

## 当前事实与约束

列出已检查的代码路径、协议证据、兼容要求、用户数据边界和未知项。

## 实施阶段

- [ ] 阶段 1：<可验证结果>
- [ ] 阶段 2：<可验证结果>
- [ ] 阶段 3：<可验证结果>

## 具体改动

按文件或模块描述预期行为和接口，不粘贴大段最终代码。

## 验证与验收

列出命令、预期输出、失败判据，以及何时需要真实远端烟测。

## 进度记录

- YYYY-MM-DD HH:mm — 完成/正在做/下一步；附可复现证据。

## 意外发现

记录改变原假设的事实和证据；没有时写“暂无”。

## 决策记录

- 决策：...
  理由：...
  日期：...

## 恢复与回滚

说明中断后从哪里继续，以及失败时如何安全撤销本任务产生的状态。

## 结果总结

完成时对照目标说明结果、验证、遗留问题和后续建议。
```

计划不是对话转录，也不是永久产品规范。稳定结论应回写到代码、测试、`AGENTS.md` 或相应
harness 文档中，完成计划保留的是实现历史和决策上下文。
