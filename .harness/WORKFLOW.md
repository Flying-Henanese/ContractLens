# Agent Development Workflow

## 1. 建立事实

开始修改前：

1. 阅读根 `AGENTS.md` 和 `.harness/README.md`。
2. 运行 `git status --short`，保留与任务无关的用户改动。
3. 用 `rg` 定位实现、调用点、模型和测试，不仅凭文件名推断。
4. 明确验收标准、兼容边界和最小改动面。
5. 只有涉及服务参数或模型行为时才检查远端；普通单元测试必须保持离线。

## 2. 决定是否写执行计划

以下任一情况应按 [`PLANS.md`](PLANS.md) 创建计划：

- 改动跨越两个以上职责层，例如客户端协议同时影响归一化和模型。
- 修改输出契约、失败策略、并发模型或印章坐标逻辑。
- 工作需要多个可独立验证的阶段，或可能由另一个智能体继续。
- 存在迁移、回滚、真实数据烟测或尚未确认的外部依赖。

局部修复、文案或单文件低风险调整可直接实施，但仍必须验证。

## 3. 实施原则

- 保持修改范围与用户任务一致，不顺手重构无关代码。
- 先在最接近不变量的层修复根因，再更新调用方。
- 用户可见行为变化时同步 README；稳定开发方式变化时同步 harness。
- 请求或响应形状变化时补 `test_client.py`；拆页变化补 `test_ingestion.py`；归一化、表格或
  印章变化补 `test_normalization.py`；并发和页序变化补 `test_service.py`；CLI 变化补 CLI 测试。
- 测试使用动态最小 PDF 或裁剪后的字典，不保存真实大响应和 Base64。
- 依赖只通过 `uv add` / `uv add --dev` / `uv sync` 管理，不使用系统 `pip`。

## 4. 确定性验证

优先运行与改动最接近的单项测试，迭代完成后运行完整门槛：

```powershell
& .\.harness\scripts\check.ps1
```

也可分开运行：

```powershell
& .\.harness\scripts\check.ps1 -Mode Lint
& .\.harness\scripts\check.ps1 -Mode Test
```

改动涉及 PaddleX 请求协议、真实响应归一化或坐标时，并且远端可用，追加：

```powershell
& .\.harness\scripts\smoke.ps1 -InputPdf "resources\...\sample.pdf"
```

烟测必须写入 `output/smoke/`。远端不可用时，清楚报告未运行的验证，不用模拟成功替代它。

## 5. 自我评审

交付前检查 `git diff` 并逐项回答：

- 改动是否保持模块边界和 fail-fast 语义？
- 是否存在泄漏正文、Base64、完整响应或代理误用？
- 是否错误地把远端当前状态写成本地永久事实？
- 坐标是否来自同一页面坐标系，polygon 是否全部点完成转换？
- 输出字段、引用 ID 和字符偏移是否向后兼容？
- 新行为是否有失败路径、边界值和回归测试？
- 文档、脚本和实现是否仍一致？
- 是否意外修改了 `resources/`、根目录样例或无关用户文件？

## 6. 交付内容

最终说明只包含可核验信息：

- 已实现的结果和关键设计选择。
- 修改的主要文件。
- 实际运行的验证命令及结果。
- 未运行的远端验证、剩余风险或需要用户决定的事项。

不要声称未运行的测试通过，也不要把“代码看起来正确”当作验证结果。
