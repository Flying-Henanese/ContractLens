# 表格与印章 VLM 兜底可行性调查

状态：completed
负责人：Codex
创建日期：2026-07-31
完成日期：2026-07-31

## 目标

在不修改业务代码的前提下，使用 `resources/4-4通用表格/` 中的真实 PDF 验证以下链路：

```text
PaddleX 检测表格/印章
  -> 取得已检测元素的 bbox 和 layout score
  -> 内存渲染或使用 PaddleX 印章 crop
  -> qwen3.6-27b 严格 JSON Schema 转写
  -> 程序化语义校验
  -> 无法辨认、失败或不一致时保留 PaddleX
```

本调查不建立正式阈值或人工真值集。视觉检查只用于发现明显错字、漏项、补齐和不稳定性，
不能代替后续正式质量评测。

## 已确认配置与边界

- PaddleX：`http://192.168.0.67:8880/layout-parsing`。
- VLM：`http://192.168.0.194:8000/v1/chat/completions`，
  model=`qwen3.6-27b`。
- 只测试已检测到的表格和印章，不检查完全漏检元素。
- VLM 单次超时先按 30 秒测试；最多 5 次只用于传输错误、429 或可重试 5xx。
- 提示词禁止推断、补全、纠错和使用外部知识；任一部分不清楚应返回 `null`。
- PaddleX 文本不发送给 VLM，避免错误候选产生锚定。
- 图片、Base64、完整 VLM 响应和业务正文不写入本报告或运行日志；临时裁剪在核验后清理。

## 样本

从 10 份、共 13 页通用表格 PDF 中选择了以下视觉类型：

- 旋转扫描表格，包含大面积印章遮挡。
- 清晰多列表格，包含印章覆盖表头。
- 蓝底多列表格。
- layout score 较低的小字号扫描表格。
- 三枚不同清晰度和不同叠字程度的印章。

样本覆盖了旋转、低分辨率、小字号、彩色背景、印章遮挡和正文叠印，但不是统计意义上的
测试集。

## PaddleX 响应发现

### 表格没有可直接使用的内容置信度

- 抽样表格的 `layout_det_res.boxes[].score` 约为 `0.9086` 到 `0.9706`。
- 表格 `parsing_res_list` 含 HTML，但没有 `layout_score`、OCR score 或 cell score。
- 同页没有可与表格单元格配对的 `overall_ocr_res.rec_scores`。
- 视觉困难、内容有错的扫描表格仍可能获得约 `0.95` 的 layout score。

因此 layout score 只能说明“表格框检测可信”，不能说明表格内容正确。当前远端协议不能直接
实现“表格内容置信度低才调用 VLM”。表格还需要结构异常、空值模式、格式校验或新的服务端
cell/OCR score 作为触发信号。

### 表格检测框可能小于实际解析范围

旋转扫描表格的 layout bbox 只覆盖到可见的部分行，而 PaddleX HTML 包含 bbox 外的后续行。
直接按 layout bbox 加很小 padding 裁剪会截断表格。表格 crop 必须使用更大的类型专用扩框、
服务端表格 crop，或能证明覆盖完整表格的区域来源。

### 印章 crop 可直接获得

抽样印章都可从 `markdown.images` 中按 bbox 名称取得对应裁剪图，不需要持久化或重新裁剪。
但是印章 crop 可能同时包含黑色正文、表格线和红色印泥。

## VLM 结果

### 时延

| 类型 | 30 秒结果 | 较长单次调用 |
| --- | --- | --- |
| 印章 | 通常 1–2 秒返回；一个样本 18.7 秒后因输出截断被拒绝 | 未需要延长 |
| 清晰 7 行多列表格 | 5 次均超时，累计约 161 秒 | 90 秒上限下约 46.9 秒完成 |
| 蓝底 4 行多列表格 | 30 秒超时 | 约 37.7 秒完成 |
| 小字号 20 行扫描表格 | 30 秒超时 | 低分辨率约 83.7 秒，高分辨率约 73.7 秒完成 |
| 扩框后的大型扫描表格 | 未重复 5 次 | 90 秒仍超时 |

结论：30 秒适合作为印章单次超时，不适合作为完整表格 HTML 的统一超时。表格请求重试 5 次
会放大最坏延迟和 GPU 消耗；同一确定性请求超时后重复 5 次没有观察到收益。

### 印章

- 一枚表格文字叠印的印章：VLM 把红色印章文字和黑色表格文字混为一体，并错误返回
  `readable`。
- 对同一印章做红色分离后，两个不同分辨率版本返回了两个不同的公司名，其中一个还新增了
  图中不能可靠确认的编号。
- 一枚扫描印章：VLM 将省份和公司名识错，但仍返回 `readable`。
- 一枚正文严重叠印的印章：模型没有在 token 上限内结束，结果按规则拒绝；PaddleX 原结果
  得以保留。

印章颜色分离能减少黑色正文干扰，但不能让模型可靠遵守“任何字符不清就返回 null”。对同一
crop 的多视图结果不一致可以作为拒绝条件，不能作为正确性证明。

### 表格

#### 清晰表格

较长超时后，VLM 的 9 行、75 单元格结果与 PaddleX 内容基本一致，仅有标点和空格差异；
没有观察到可确认的内容救回。该结果证明链路和表结构 Schema 可工作，但没有增益。

#### 蓝底表格

90 秒上限下约 37.7 秒完成。VLM 与 PaddleX 均返回 6 行、100 单元格，逐单元格文本一致；
没有内容增益。

#### 印章遮挡的旋转扫描表格

VLM 返回 `readable`，但出现以下不可接受行为：

- 行号识别错误。
- 在印章遮挡、原图不可可靠读取的单元格中按相邻行规律补齐数值。
- 丢失列和尾部行后仍声称完整可读。

扩大 crop 后完整表格在 90 秒内仍未完成。该样本中 PaddleX 对遮挡区保留空值，比 VLM
生成式补齐更安全。

#### layout score 较低的小字号扫描表格

- PaddleX、低分辨率 VLM、高分辨率 VLM 都返回相同的 21 行、231 单元格结构。
- 低分辨率与高分辨率 VLM 有 48 个单元格文本不同。
- 高分辨率 VLM 与 PaddleX 有 19 个单元格文本不同。
- 视觉检查确认高分辨率 VLM 修正了少数 PaddleX 表头或正文错字；同时也引入了新的错误。
- 两次 VLM 都将整表标记为 `readable`，没有诚实暴露不确定性。

这是本轮唯一观察到局部“可能救回”的样本，但整表结果不满足自动覆盖门槛。分辨率变化导致
大量文本变化，说明当前输出不稳定。

## 结论

### 已验证可行

- PaddleX 检测框到内存 crop、VLM 图像请求、严格 JSON Schema 和程序化解析的技术链路可通。
- 印章 crop 可以可靠取得，且单次推理通常远低于 30 秒。
- 高分辨率表格 crop 能让 VLM 修正少量 PaddleX OCR 错字，证明大模型有局部补救潜力。
- VLM 失败、超时、截断或语义校验失败后保留 PaddleX 的 soft-fail 路径可执行。

### 尚不可用于自动覆盖

- 模型不能可靠遵守“任一部分不清楚就返回 null”，会对遮挡内容进行生成式补齐。
- `status=readable` 不是可信证据；严格 JSON Schema 只能保证形状。
- 表格没有内容置信度，当前仅靠 layout score 无法选择真正需要兜底的表格。
- 整表 HTML 生成明显超过 30 秒；5 次重复尝试不可接受。
- 同一表格不同分辨率下结果不稳定，且没有无人工真值即可判定正确的接受规则。

## 建议

1. 暂不创建“自动替换生产结果”的功能分支。
2. 若继续开发，先建立 `shadow-only` 原型分支：
   - VLM 默认关闭且绝不修改现有 JSON 内容。
   - 只记录非敏感指标：元素类型、bbox score、耗时、状态、结构和一致性计数。
   - 图片、正文、PaddleX/VLM 完整结果不持久化。
3. 印章采用红色分离加原图双视图；只有两个视图完整文本严格一致才进入后续验证，否则保留
   PaddleX。严格一致只能减少风险，不能证明文本正确。
4. 表格使用高分辨率渲染和类型专用扩框。30 秒超时保留给印章；完整表格建议单次 90 秒上限，
   最多 1 次，不对确定性超时重试。
5. 表格接受策略需要重新设计。候选方向：
   - 服务端补充 cell/OCR score 和 cell bbox；
   - 用结构/格式规则只定位可验证的疑似错误单元格；
   - VLM 按行或按小区域识别，并要求多视图一致；
   - 在没有可验证接受规则前保持 shadow，不覆盖 PaddleX。
6. 如果产品必须坚持“表格任一部分不清即整表 null”，则大多数真正困难表格应被拒绝；
   不能依赖模型自报 `readable` 自动放行。
